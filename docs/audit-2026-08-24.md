## 1. Chess End-to-End Quality Audit

Walking the full Chess flow in sequence, each step tagged by severity: **[CRITICAL]** blocks or misleads around money, **[HIGH]** dead end or broken UX, **[MEDIUM]** PoC tell, **[LOW]** polish gap.

### Step 1 — Sign In & Onboarding (`SignInPage.tsx`)

**What's good:** Auth flow is multi-step, all errors are handled inline via `friendlyAuthError()`, and all loading states use `<Centered>Loading…</Centered>` (minimal but present). The excluded-state path explicitly tells the user "Cash play is not available in {state} yet."

**Friction points:**

- **[MEDIUM]** Username placeholder is `"kvem_"` — a real developer handle, not a generic example. First impression is PoC.
- **[HIGH]** No Terms of Service or Privacy Policy link anywhere at account creation. For a money product this is a regulatory red flag and a trust signal gap for any serious user.
- **[MEDIUM]** The step progress indicator shows dots 1→2→3 with no text labels. A user has no idea what "step 2" requires.
- **[MEDIUM]** `"Skip sign-up · enter the demo →"` is always visible below a separator during the auth step. It's a conversion leak — a real-money-curious user might take the demo path because it looks like the fast option.
- **[LOW]** No confirmation email copy or success state for account creation — user is immediately pushed into onboarding without any "you're in" moment.

### Step 2 — Linking a Lichess Account (`LinkGames.tsx`)

**What's good:** Loading state is a pulsing `<SkeletonList rows={3} />`. Per-account states (LINKED, UNLINKED, BLOCKED) are distinct. Server error messages surface correctly from the API.

**Friction points:**

- **[MEDIUM]** The text input placeholder for all non-Dota games is `'Your username'` — generic, not Lichess-specific. It should say "Your Lichess username" or "e.g. MagnusCarlsen".
- **[HIGH]** No link to lichess.org from the linking form. A new user who doesn't know their exact Lichess handle has no escape hatch and no guidance.
- **[CRITICAL]** Linking is **irreversible from the UI** — `DELETE /links/{game}` is admin-only. There is no copy anywhere warning the user this is permanent. No "contact support to change it" affordance. If a user types the wrong handle they are silently stranded.
- **[HIGH]** The links load error state (`"Couldn't load your games."`) has no retry button. If the endpoint is slow on first load, the user sees a dead-end error message with no path forward.
- **[LOW]** The LINKED state shows `{host_username} · {total_games} games` but no link to the Lichess profile. Users cannot verify the right account was linked without leaving the app and searching manually.

### Step 3 — The Play Page (`PlayPage.tsx`)

**What's good:** Error state has a retry button. Not-linked state shows a clear CTA to Profile. Markets are well-structured.

**Friction points:**

- **[CRITICAL]** Chess speed (bullet/blitz/rapid/classical) is **silently forced to blitz** (the middle index of `market.speeds`) via `defaultSpeed()`. There is no speed picker visible in the UI. A user who plays rapid or classical is entered into blitz games without knowing it. The "BLITZ" tag on the card is read-only display.
- **[MEDIUM]** `capacity={2} filled={1}` is **hardcoded** on every `WagerCard` (PlayPage.tsx lines 209–210). The fill dots are meaningless scaffolding — they always show 1/2 regardless of queue depth.
- **[LOW]** "Waiting to play" section (users who can be directly challenged) simply hides when empty. No copy explaining what it is or how players end up there.

### Step 4 — Finding a Match & Confirming (`PlaySlip.tsx`)

**What's good:** Searching state has live stage copy ("Widening the search for a fair match…"), a second counter, and a cancel button. The matched state shows pot, prize, fee, and a win forecast before the user commits — this is the best disclosure moment in the flow.

**Friction points:**

- **[HIGH]** `your_play_url` (the Lichess challenge link) **can be null** if `broker.get("urls")` is absent or `seat.color` is null at activation time (`match_lifecycle.py` line ~176). When null, `PlaySlip` silently falls through to the generic "Jump into CHESS and play" copy — no link, no error, no explanation. The user has confirmed, escrowed money, and has nowhere to go.
- **[MEDIUM]** Opponent name falls back to `'Opponent'` if username is null. Rare edge case but jarring when it appears.

### Step 5 — Activity / Results (`ActivityPage.tsx`, `ActivityCard.tsx`)

**What's good:** Settlement toast fires on new result. Status labels (Won/Lost/Push/Refunded) are clear. Retry exists on error.

**Friction points:**

- **[HIGH]** The expanded `ActivityCard` for a chess H2H match shows an **empty stat compare table**. Grading for `win_h2h` stores only `winner_user_id` + `host_game_id` — no per-seat stat lines. Users see nothing in the detail section, which looks broken.
- **[HIGH]** The `host_game_id` Fact chip (the Lichess game ID) is shown as plain text. There is **no hyperlink to `https://lichess.org/{game_id}`**. A user who wants to review the game has no direct path from the app.
- **[MEDIUM]** Empty state CTA is "Browse solo pools" (`/pools`) — wrong target for a H2H chess user.
- **[LOW]** "No details for this one." is shown if `item.detail` is falsy — no further explanation.

### Step 6 — Profile Page (`ProfilePage.tsx`)

**Friction points:**

- **[MEDIUM]** The CS2 Steam setup section ("Connect Steam and your matches settle your wagers automatically") and `<Cs2SetupCard />` are **rendered for all users regardless of whether they play CS2**. A chess-only user sees a prominent CS2 section with no way to dismiss or hide it.
- **[LOW]** `chess_accuracy` is listed in constants as a metric but has no data source (Lichess only provides it for games with requested analysis). It is deliberately retained but indistinguishable from a mistake without reading the comment in `constants.py`.

### Chess UX Summary

| Severity | Count | Top items |
|---|---|---|
| CRITICAL | 2 | Linking is permanent with no warning; chess speed is silently forced |
| HIGH | 5 | No unlink from UI; no Lichess link on form; play_url can silently be null; empty stat compare; no game link from Activity |
| MEDIUM | 6 | "kvem_" username, hardcoded filled/capacity, generic placeholder, CS2 section for all users, empty searching tooltip |
| LOW | 4 | No Lichess profile link, activity CTA mismatch, empty detail fallback, chess_accuracy retained |

## 2. Core Product Evaluation

### 2.1 Skill Contracts

**Status: IMPLEMENTED**

A "skill contract" is structurally a **ledger-backed state machine**, not a single object. For H2H it is three tables: `queue_tickets` (waiting slot, no escrow), `matches` (the formed contract with frozen economics), and `match_players` (one seat each). Equivalent patterns for `solo_pools` + `solo_entries` and `tournaments` + `tournament_entries`.

All economics are frozen at contract formation and stored as integer cents:
- `entry_cents`, `rake_bps`, `pot_cents`, `prize_cents`, `rake_cents` — immutable after creation
- A `CHECK` constraint on `matches` enforces `pot_cents = prize_cents + rake_cents`
- Settlement writes `escrow_hold → escrow_release + payout + rake` as separate `ledger_entries` rows, then asserts conservation before committing

**Files:** `models/play.py`, `models/pools.py`, `models/tournaments.py`, `services/match_lifecycle.py`, `services/pool_engine.py`, `services/money_math.py`, `services/wallet_service.py`

Entry amounts are constrained to presets `$5 / $10 / $25` (`ENTRY_PRESETS_CENTS`, `constants.py:214`). Arbitrary amounts are rejected at enqueue. The `BaselineSnapshot` freezes (μ, σ, n) at ticket creation so settlement always replays from stored state — no re-query of the host.

### 2.2 ELO / Skill Buckets

**Status: PARTIAL**

**Implemented:**
- Per-player, per-game, per-metric skill model stored in `metric_models` table as (μ, σ, n)
- EWMA over recent match history, half-life 10 matches (`metric_models_service.compute_ewma()`)
- Chess-only: Elo-informed prior + shrinkage (`skill_prior.shrink()`), with prior derived from 4,526 Lichess games
- Difficulty tiers: easy (k=0.385 → ~35% clear rate), medium (k=0.842 → ~20%), hard (k=1.282 → ~10%)
- H2H pairing: `P(a beats b) = Φ((μa−μb)/√(σa²+σb²))` must fall in `[0.5±w]` with a widening ladder
- Pool composition: each member's clear probability vs. room bar must be in `[p_target/2, min(2·p_target, 0.5)]`

**Partial / absent:**
- **No global categorical ELO bucket.** There is no Bronze/Silver/Gold tier or ELO band labeling in the consumer UI. Bucketing is per-market probabilistic math, not a named tier system.
- Shrinkage (blending observed data with a population prior) works **for chess only** — `_PRIORS` dict is empty for CS2, PUBG, Dota. All three games use raw EWMA with no shrinkage.
- Chess Elo band pairing (band starts at 100, widens 12 Elo/sec, max 800) uses the linked account's Lichess rating directly as an Elo proxy. This is solid.

**Files:** `services/metric_models_service.py`, `services/skill_prior.py`, `services/pairing.py`, `services/fairness.py`, `constants.py`

### 2.3 Bucket Odds / Standardization

**Status: PARTIAL (disclosed probability, not odds)**

The system does not use odds lines. It uses a **disclosed clear probability** — the `clear_prob()` function in `fairness.py` computes `1 − Φ((bar−μ)/σ)` (or lognormal variant for chess) and returns it rounded to 4 decimal places. Pool cards show this as a percentage ("Est. clear rate: 34%").

What exists:
- `fairness.clear_prob()` — disclosed probability per tier per player (`fairness.py:128`)
- `preview_bars()` — returns `clear_rate` alongside the bar value for pool card display (`pool_engine.py:194`)
- `forecast_between()` — returns `P(you beat opponent)` as a plain-English label on the H2H matched slip (`matchmaking.py:325`)
- Display multiplier: `pool_multiplier_estimate_bps() = round((1−rake)/p_target)`, capped at `room_size·(1−rake)` — display only, not a banked payout line (`money_math.py:84`)

What does not exist:
- No cross-game normalization. Each metric is its own independent (μ, σ) world.
- No "bucket odds" in a sportsbook sense — the platform never sets an odds line or takes outcome risk.
- No calibration harness comparing predicted clear rates to realised ones.

**Files:** `services/fairness.py`, `services/money_math.py`, `services/pairing.py`

### 2.4 Result Verification

**Status: IMPLEMENTED (fully server-authoritative, zero self-reporting)**

All results are fetched from host APIs server-side. No client endpoint accepts a result or stat value. The `raw_payloads` table stores the exact host response with a SHA-256 hash.

| Game | Method | API Called | File |
|---|---|---|---|
| Chess | `adapter.match_winner()` → Lichess REST | `GET /game/export/{game_id}` — verifies both accounts played, checks winner | `adapters/chess_lichess.py:90–112` |
| CS2 | GC sidecar → stored `cs2_matches` → adapter reads from DB | Share code → protobuf → scoreboard stored | `adapters/cs2_steam.py`, `services/cs2_chain.py`, `gc-sidecar/` |
| Dota 2 | `adapter.poll_eligible_games()` → OpenDota | `/players/{id}/matches` | `adapters/dota2_opendota.py` |
| PUBG | `adapter.poll_eligible_games()` → PUBG API | Official API, 9 req/min throttle | `adapters/pubg.py` |

Grading dispatch is in `services/grading.py:211`. Chess (brokered) uses `_grade_brokered()` which resolves the **specific game the platform created** via Lichess open challenge — a player cannot substitute a different game. CS2/Dota/PUBG use `_grade_coordinated()` which looks for each player's first eligible match after `matched_at`.

### 3.4 Admin Portal

**How to access:** Navigate to `/admin`. Requires `role = 'admin'` on the user row. Grant with:
```
cd apps/api && uv run python ../../scripts/grant_admin.py <email>
```
Frontend also enforces the role guard (`RequireAdmin.tsx`); server independently enforces `require_admin` on every `/admin/*` route.

**Admin sub-pages and functions:**

| Page | Route | Function |
|---|---|---|
| Users | `/admin/users` | Search users; view linked accounts + contests + ledger; Freeze/Unfreeze; Adjust ledger with required reason |
| Contests | `/admin/contests` | Filter by state/game; view match/pool/tournament detail with raw adapter evidence JSON; Re-settle or Void (with reason) |
| Disputes | `/admin/disputes` | Open dispute queue; per-dispute resolution input; Resolve / Reject |
| Flags | `/admin/flags` | Feature flag toggles (queue_paused, settlement_paused, per-game on/off); `geo_config` excluded-states editor |
| Queue | `/admin/queue` | Live queue depth per game/market/tier; average wait time; auto-refreshes every 5s |
| Reconciliation | `/admin/reconciliation` | Global solvency check; settlement worker heartbeat; per-contest conservation violations |
| Risk | `/admin/risk` | Per-market rate drift (offered/accepted/settled); expected vs. actual win rates; sandbagging flag queue |

**What's broken or rough:**
- Contest state filter is a free-text input with `placeholder="state (e.g. ACTIVE)"` — no dropdown validation. A typo silently returns no results.
- Ledger adjustment input is plain text with `placeholder="cents (+/-)"` — no guard against non-numeric input at the UI level.
- Layout uses hardcoded hex colors and `style={}` inline throughout — no responsive design, no dark mode, no accessible labels on inputs.
- Not keyboard-accessible (no `<label>` associations on most inputs).

### 3.5 First-Bet / Contract Flow

**Full decision count, cold-start first-time user (Pools path — default landing):**

| # | Decision / Input | Screen |
|---|---|---|
| 1 | Choose auth method: Google vs. email vs. demo | `/signin` |
| 2 | Enter email | `/signin` |
| 3 | Enter password | `/signin` |
| 4 | Enter or confirm username | Onboarding |
| 5 | Select residence state (50-item dropdown) | Onboarding |
| 6 | Check age attestation checkbox | Onboarding |
| 7 | Select one or more games | Pick games step |
| 8 | Link a game account (or skip) | Link games step |
| 9 | Select game tab on Pools page | `/pools` |
| 10 | Select metric (if >1 for game) | `/pools` |
| 11 | Select difficulty (Easy / Medium / Hard) | `/pools` |
| 12 | Select entry amount ($5 / $10 / $25) on the WagerCard | `/pools` |
| 13 | Confirm entry in the card confirmation step | `/pools` |

**Total: 13 decisions before first wager is committed.**  
**Returning user (re-entering after first wager): 4 decisions + 1 confirm = 5.**

**Where can this be cut:**
- Decision 7 (Pick games) adds nothing — game tabs are visible on every page. Remove this step.
- Decisions 10–11 (metric + difficulty) could default to "most popular" or "easy" with an "Advanced" disclosure, reducing the cold-path count by 2.
- Decisions 2–3 collapse to 1 click with Google SSO — encourage that path more prominently.

**Minimum achievable cold-start count:** ~8 decisions (auth method, Google OAuth consent, username, state, age, game tab, entry amount, confirm).

**Where the rake/fee is disclosed:**
- **H2H:** `PlaySlip.tsx` line ~80–94 renders `"Both stake $X · winner takes $Y · $Z platform fee"` — visible after matching and before confirming. This is the correct moment.
- **Pools:** The fee is **not shown on pool cards before joining**. `WagerCard` shows "Est. win" (which is net of rake) but never shows the rake explicitly. A user does not see the 10% fee before they confirm pool entry.

**What can collapse into "Advanced":**
- Difficulty selection (most users will pick Easy first)
- Metric selection (most games have a primary metric; others can hide behind "Advanced")
- Time control / speed for chess (default blitz; Advanced shows bullet/rapid/classical)

- **The rake** — as noted above, not shown on pool cards before joining.

### 4.3 Main Data / Settlement Path

```
User → POST /play/queue → matchmaking.enqueue()
  → geo_service.assert_can_enter()          # first, before any DB write
  → limits_service checks                   # balance, daily caps, concurrency
  → QueueTicket created (baseline frozen, personal_bar computed, no escrow)
  → _pair_ticket(): forecast_prob ∈ [0.5±w], can_pair() → Match(PENDING) + 2 MatchPlayers

User → POST /play/{match_id}/confirm → match_lifecycle.confirm()
  → geo_service + limits_service re-check
  → wallet_service.escrow_hold()            # money moves here
  → if both confirmed: _activate()
    → (chess) adapter.create_match() → host_game_id + play_url stored
    → (others) matched_at stamped, players go play

settlement_worker.run_cycle() every 15s:
  → _sync_share_chains()                    # CS2 only: resolve new share codes via GC sidecar
  → _process_due_matches():
      grading.grade() → GradeOutcome
      → HostUnavailable: extend window (no money movement)
      → Hard ceiling passed: CANCEL + refund
      → WIN/PUSH: raw_payload persisted → match_lifecycle.settle()
          → wallet_service: escrow_release + payout + rake (WIN)
          → wallet_service: refund (PUSH/CANCEL)
          → reconciliation_service.check() — breach → ReconciliationError → worker halts
  → _process_due_pools(): telemetry_fetch → pool_engine.settle_pool()
  → _process_due_tournaments(): telemetry_fetch → tournament_engine.settle_tournament()
```

### 4.4 Game-Specific Logic Leaking into Core

| Location | Type | Severity |
|---|---|---|
| `settlement_worker._sync_share_chains()` | CS2 chain sync called by name in the shared worker loop | **Structural** — the one real seam violation; isolated (swallows all exceptions, gated by `cs2_chain.is_enabled()`), but not game-agnostic |
| `matchmaking.py` comment line ~201: "chess — Elo band" | Informational comment; code dispatches on `market.kind` not game name | Minor |
| `grading.py` comments label `win_h2h` as "(chess)" | Informational only | Minor |
| `routers/cs2.py` | Intentional dedicated router for CS2 share code intake | By design — CS2 has unique intake mechanics with no equivalent |
| `routers/demo.py` (metric name hardcodes) | Demo-only path; not production logic | Acceptable |

**What is fully game-agnostic:** `wallet_service.py`, `money_math.py`, `reconciliation_service.py`, `pool_engine.py`, `tournament_engine.py`, `match_lifecycle.py`. None import a concrete adapter. All reference adapters only through `registry.get(game_id)`.

### 4.5 Dead Code, Duplication, Day-One Confusion

**Dead code:**
- `adapters/__pycache__/cs2_faceit.cpython-312.pyc` — stale bytecode from the removed FACEIT adapter. Harmless but misleading to a new developer who wonders if FACEIT is still in play.
- `services/test_opponents.py` — labeled "This module is scaffolding. Delete it before launch." Lives in `services/` (not `tests/`), accessible at runtime, and is referenced by three router call sites. A new developer doesn't know whether to treat it as production or test code.
- `chess_accuracy` in `METRIC_MARKETS` (`constants.py`) — no data source; Lichess only provides it for games with manually requested analysis. Retained intentionally but indistinguishable from an oversight without reading the inline comment.
- `cs2_adr` reference in `METRIC_BAR_INCREMENT` — retired in migration 0024. Still present in constants (fixed on `fixes/testing` but worth verifying it's removed).

**Duplication:**
- `_metric_model()` query (select MetricModel where…) is independently copied in `matchmaking.py:133` and `pool_engine.py:137`.
- `_now()` (returns `datetime.now(UTC)`) is independently defined in `match_lifecycle.py`, `matchmaking.py`, `pool_engine.py`, `tournament_engine.py`, `settlement_worker.py`, `telemetry_fetch.py` — six copies. Convention not abstracted into a shared utility.

**Day-one confusion for a new developer:**
1. **`test_opponents.py` in `services/`** — its location implies it is production; its docstring says delete it.
2. **Three `_now()` functions** — a new agent who wants to mock time has to patch six locations.
3. **Settlement worker has no interface/ABC** — its `run_forever()` and `run_cycle()` methods are called directly; a new game integration can't tell where to hook in.
4. **The `cs2_chain.py` sync** is referenced directly in the worker, not through the adapter. A new game integration that also needs a polling/sync step has no documented pattern to follow.
5. **`config.py` fails fast on missing required vars** — good, but `.env.example` doesn't distinguish required-for-local-dev vs. required-for-production. A new developer running locally will hit `SENTRY_DSN` and `POSTHOG_KEY` errors when those are optional.

### 4.6 GameAdapter Interface Verification

**File:** `adapters/base.py`

**Abstract methods (must implement in every adapter):**

| Method | Signature | Purpose |
|---|---|---|
| `link_account` | `(method: str, identifier: str) → ProfileSnapshot` | Verify host account exists, return skill profile |
| `fetch_profile` | `(account_id: str) → ProfileSnapshot` | Re-fetch profile for already-linked account |
| `poll_eligible_games` | `(account_id: str, since_ms: int, filters: GameFilters) → list[NormGame]` | Return finished eligible games since timestamp |

**Non-abstract with default-raises (brokered adapters only):**

| Method | Default | Purpose |
|---|---|---|
| `create_match` | `raise NotImplementedError` | Platform creates the game on the host |
| `match_winner` | `raise NotImplementedError` | Resolve brokered game by id |
| `live_match` | `return None` | Best-effort live game state |

**Class attributes:** `id: str`, `brokered: bool = False`, `defer_bootstrap: bool = False`

**Investor/partner note on naming:** The interface does not use the term "resolveContract" — the closest equivalents are `match_winner` (adapter, for brokered games) and `grading.grade()` (service, for all games). The term "skill contract" is product framing, not a code construct.

**`ChessLichessAdapter`:** Fully implements all six methods. No stubs.

## 6. Separation-of-Concerns Check

### The Three Layers

| Layer | Isolation | Verdict |
|---|---|---|
| Core money infra (`wallet_service`, `money_math`, `reconciliation_service`, `match_lifecycle`) | Fully game-agnostic — zero game names, no adapter imports, pure money operations keyed by `(user_id, amount_cents, ref_type, ref_id)` | **Clean** |
| Game adapter layer (`adapters/` + `registry`) | Clean ABC in `base.py`; single indirection via `registry.get(game_id)`; engines never import a concrete adapter | **Clean** |
| Game-specific verification (`cs2_chain.py`, `gc-sidecar/`, `routers/cs2.py`) | CS2's intake path (share code → GC sidecar → stored rows) is unique and has no adapter-level equivalent | **Intentional exception** |

### Can One Game's Adapter Fail Independently?

**Yes**, for host outages. The grading service catches `HostUnavailable` and returns `PENDING` → the worker extends the window without settling. The pool and tournament engines catch `HostError` and refund unverifiable entries. The CS2 chain sync explicitly swallows all exceptions ("Never fatal to a cycle. Valve being slow must not stop pools and matches from settling.").

**`ReconciliationError` cascades to halt the entire worker** — this is the only cross-game cascade, and it is intentionally fail-closed. A conservation breach in one CS2 match will pause settlement for chess matches too, until an admin clears it. This is correct behavior (the books are wrong; stop everything) but worth documenting as an explicit design choice.

### The One Real Seam Violation

`settlement_worker._sync_share_chains()` is a CS2-named function called directly in the shared worker cycle. It is:
- Gated by `cs2_chain.is_enabled()`
- Exception-isolated (all exceptions swallowed)
- Commented explicitly as "CS2's intake mechanism is what makes CS2 different from other games"

It cannot be moved behind the `GameAdapter` ABC without redesigning the interface to include a `sync_intake()` or `pre_cycle_hook()` method. For other games this method would be a no-op. Whether to add that abstraction depends on whether another game (e.g., a future title with its own scoreboard API) needs a similar intake loop.

### Would a New Game Integration Break Existing Games?

**No**, under normal circumstances. Adding a new adapter requires:
1. Implementing the `GameAdapter` ABC in a new file under `adapters/`
2. Registering it in `registry.py`
3. Adding constants for the game's metrics in `constants.py`
4. Writing a migration to seed the `feature_flags` kill switch row

The pool engine, tournament engine, settlement worker, and wallet service require no changes. The only worker change needed is if the new game has a CS2-style intake loop — at which point `_sync_share_chains()` becomes a pattern to generalize.

**The one integration-breaking risk is infra-level, not code-level:** the CS2 GC sidecar is a single Node.js process connecting to a single automated Steam account. Valve rate-limiting or banning that account would stop all CS2 settlement without affecting other games — but Valve's terms of service exposure and the single-Steam-account design are the vulnerability, not the code architecture.
